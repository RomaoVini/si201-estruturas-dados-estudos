1. Notação O (lê-se "ó")

1.1 A ideia intuitiva

Imagine que você está comparando dois corredores em uma maratona de 10 km. Um deles as vezes acelera, as vezes desacelera, mas você sabe que nunca vai ultrapassar um ritmo de 6 min/km a partir do 3º km. Essa é a essência do O: um teto de crescimento, válido a partir de um certo ponto, e ignorando os primeiros quilômetros (valores pequenos de n).

Em algoritmos, "ritmo de crescimento" é o número de operações (ou o tempo) em função do tamanho da entrada n. Dizer que um algoritmo é O(n²) é dizer: "o número de operações nunca cresce mais rápido que n², a partir de um certo tamanho de entrada".

1.2 Definição formal

f(n) = O(g(n))

Existem duas constantes positivas c e n₀ tais que 0 ≤ f(n) ≤ c·g(n), para todo n > n₀.

Duas liberdades que a definição te dá, e que são exatamente o que faz a notação assintótica ser útil:

  • Você pode ignorar valores pequenos de n — a desigualdade só precisa valer a partir de n₀, não desde o início.
  • Você pode escolher a constante c — não precisa ser 1; pode ser 20, 1000, o que for necessário para a desigualdade fechar.

1.3 Prova passo a passo

Vamos mostrar que 10n² + 5n + 5 = O(n²). A primeira tentativa ingênua, com c = 10, falha:

   tentativa:  10n² + 5n + 5 ≤ 10n²   para todo n > 0     FALSO
               (o lado esquerdo tem 5n+5 sobrando)

A saída é ser generoso com a constante. Se assumirmos n > 1, então n ≤ n² e 1 ≤ n² — então trocamos cada termo pequeno por um n² "que cobre ele":

   10n² + 5n + 5  ≤  10n² + 5n² + 5n²   (trocando n por n² e 1 por n², vale p/ n>1)
                  =  20n²

Prova fechada: existem c = 20 e n₀ = 1 tais que 10n² + 5n + 5 ≤ 20n² para todo n > 1. Logo, 10n² + 5n + 5 = O(n²).

O truque que se repete em toda prova de O

Sempre que aparecer um termo de grau menor (5n, 5) somado a um termo de grau maior (10n²), assuma n > 1 e troque cada termo menor por n² — como n ≤ n² e 1 ≤ n² nessa faixa, a troca só aumenta o lado direito, o que é permitido numa prova de limitante superior.

1.4 O que O(n²) realmente agrupa

Todas as funções abaixo são O(n²): 100n², 5n² + 5n, 5n² + log n. A notação joga fora a constante multiplicativa e os termos de ordem menor — o que importa, para n grande, é só o termo dominante. Por isso 5n² e 1.000.000n² têm exatamente a mesma classe de complexidade O(n²).

Isso gera famílias de algoritmos com nome próprio:

Onde a folga aparece — e onde a notação "quebra"

É verdade que n = O(n²) (folga: o limitante é bem mais alto que o necessário), mas n = O(n) é uma afirmação justa (sem folga). Já n = O(√n) é falsa: por maior que seja a constante c escolhida, sempre existe um n grande o bastante para que n ultrapasse c√n — porque n cresce mais rápido que √n, e nenhuma constante segura essa diferença para sempre.

1.5 Contando operações de um código real

int x = 0;
for (int i = 0; i < n; i++) {
    x = x + 3;
}

Contando cada linha: a declaração e atribuição de x custa 2 operações; o for executa a comparação i<n um total de n+1 vezes (a última vez é a que falha e encerra o laço), o incremento i++ ocorre n vezes, e o corpo x=x+3 ocorre n vezes. Somando tudo, T(n) = 3n + 5 (aproximadamente — o exato depende de como você conta a inicialização do laço). O que importa: T(n) = O(n). Não interessa a constante 3 nem o +5 — só que o algoritmo é linear.

🟡 O2. Explique por que n² ≠ O(n), mostrando a contradição a que se chega ao tentar provar o contrário.

tente antes de abrir
Resolução comentada

Suponha, por absurdo, que existam c e n₀ tais que n² ≤ cn para todo n > n₀. Dividindo os dois lados por n (válido, pois n > 0): n ≤ c. Isso diria que n nunca ultrapassa a constante c — mas n cresce sem limite, então qualquer c escolhido será ultrapassado por algum n maior que ele. Contradição. Logo, não existe tal c, e n² ≠ O(n).

2. Notação Θ (lê-se "teta")

2.1 A ideia intuitiva

Se O é só o teto, Θ é o "sanduíche": a função fica presa entre um piso e um teto, os dois proporcionais a g(n), a partir de um certo ponto. Enquanto O permite folga (dizer n = O(n²) é válido, mesmo sendo uma afirmação frouxa), Θ exige que a função realmente cresça no mesmo ritmo de g(n).

2.2 Definição formal

f(n) = Θ(g(n))

Existem três constantes positivas c₁, c₂ e n₀ tais que 0 ≤ c₁·g(n) ≤ f(n) ≤ c₂·g(n), para todo n > n₀.

Repare que a prova de Θ é duas provas de O em direções opostas: uma parte mostra que f(n) não cresce mais rápido que g(n) (o limite superior, igual ao que você já sabe fazer), e a outra mostra que f(n) não cresce mais devagar (o limite inferior).

2.3 Prova passo a passo

Vamos mostrar que f(n) = 100n² + 100n + 100 = Θ(n²), assumindo n > 1.

Lado de cima (mesmo raciocínio do capítulo 1):

   100n² + 100n + 100  ≤  100n² + 100n² + 100n² = 300n²

Lado de baixo — aqui a prova costuma ser mais simples, porque geralmente basta usar o próprio termo dominante da função, sem nem precisar de constante:

   n²  ≤  100n² + 100n + 100     (obviamente verdade, já que só somamos termos positivos)

Prova fechada: c₁ = 1, c₂ = 300, n₀ = 1, então 1·n² ≤ f(n) ≤ 300·n² para todo n > 1. Logo f(n) = Θ(n²).

2.4 A relação entre O e Θ

AfirmaçãoVerdadeira?
Se f(n) = Θ(g(n)), então f(n) = O(g(n))Sim — Θ é mais forte, então implica O
Se f(n) = O(g(n)), então f(n) = Θ(g(n))Não necessariamente — O(g(n)) permite folga (ex: n = O(n²) mas n ≠ Θ(n²))
Se f(n) = Θ(g(n)), então g(n) = Θ(f(n))Sim — a relação Θ é simétrica (o sanduíche funciona nos dois sentidos)
Regra prática pra decidir O vs Θ numa questão

Se a pergunta pede "um limitante" ou "prove que não é pior que", geralmente é O. Se pede "a complexidade exata" ou "o comportamento justo", é Θ. Na prática, quando você consegue provar os dois lados (superior e inferior) com a mesma função g(n), a resposta correta e mais informativa é sempre Θ — é isso que a maioria dos algoritmos que você vai analisar no curso tem.

2.5 Exercícios

🟢 T1. Mostre que 50n² + 3n = Θ(n²).

tente antes de abrir
Resolução comentada

Assumindo n > 1: lado de cima, 50n² + 3n ≤ 50n² + 3n² = 53n². Lado de baixo, n² ≤ 50n² + 3n (trivial, pois 50n² já é maior que n², e 3n só soma). Constantes: c₁=1, c₂=53, n₀=1.

🟡 T2. Dado um polinômio de grau k, P(n) = a₀ + a₁n + ... + aₖnᵏ (com aₖ > 0), explique em palavras (sem álgebra pesada) por que P(n) = Θ(nᵏ).

tente antes de abrir
Resolução comentada

Para n grande, o termo aₖnᵏ domina todos os outros — cada termo de grau menor cresce mais devagar e se torna insignificante perto dele. Isso garante o teto: a soma toda fica limitada por uma constante vezes nᵏ (some cada termo menor "arredondado pra cima" até nᵏ, igual fizemos nos exemplos anteriores). E o próprio termo aₖnᵏ sozinho já garante o piso, porque os demais termos (assumindo coeficientes não negativos, ou considerando valores grandes de n onde o termo dominante já supera a soma dos negativos) não derrubam a soma abaixo de uma fração de nᵏ. Como as duas pontas usam a mesma função nᵏ, o resultado é Θ(nᵏ), não apenas O(nᵏ).

3. Tempo de execução de algoritmos

3.1 Do código para a fórmula

Considere dois for aninhados:

for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        v[i] = i + j;
    }
}

O laço interno gasta 3n + 2 operações por execução (a condição roda n+1 vezes, o incremento e a atribuição rodam n vezes cada). Como o laço externo repete isso n vezes, e ele próprio já gasta 2n+2:

   T(n) = (2n+2) + n·(3n+2) = 3n² + 4n + 2  =  Θ(n²)

Para n = 1000, o termo 3n² vale 3 milhões, enquanto 4n+2 vale só 4002 — menos de 0,15% do total. É por isso que jogamos fora os termos de ordem menor: eles não mudam a resposta de forma perceptível, e a notação assintótica existe justamente para simplificar sem perder o que importa.

3.2 Por que a constante quase não importa (e quando importa)

Compare dois programas: T₁(n) = n·10⁻⁶s (linear) e T₂(n) = n²·10⁻⁶s (quadrático). Para n = 1.000.000:

FórmulaTempo
T₁ (linear)10⁶ · 10⁻⁶1 segundo
T₂ (quadrático)(10⁶)² · 10⁻⁶1.000.000 s ≈ 11,5 dias

Um algoritmo Θ(n²) no lugar de um Θ(n) fica um milhão de vezes mais lento para essa entrada — mesmo que as duas constantes de tempo sejam idênticas. É exatamente por isso que a análise assintótica interessa mais que uma constante de 2x ou 3x: a diferença entre classes de complexidade domina qualquer constante.

Erro clássico de programador iniciante

Calcular a média dentro do for que calcula o desvio padrão — repetindo um cálculo Θ(n) dentro de um laço que já roda n vezes, virando sem necessidade um algoritmo Θ(n²). A correção: calcule a média uma vez, guarde numa variável, e use essa variável dentro do laço do desvio padrão — o algoritmo volta a ser Θ(n). Esse é o tipo de erro que "passa despercebido" para n pequeno e vira catastrófico para n grande.

3.3 O erro da regra de três

Se um algoritmo Θ(n²) gasta 1s para um certo n, quanto gasta para 10n? A resposta não é 10s — funções quadráticas não são lineares, então regra de três direta está errada.

   T(n)   = c·n²
   T(10n) = c·(10n)² = 100·c·n² = 100·T(n)

Multiplicar o tamanho da entrada por 10 multiplica o tempo por 100 num algoritmo quadrático — não por 10. Em um algoritmo cúbico (Θ(n³)), multiplicaria por 1000. Em geral, num algoritmo Θ(nᵏ), aumentar a entrada em um fator m multiplica o tempo por mᵏ.

3.4 Estimando quanto n cabe em um tempo dado

Um tipo de questão muito comum: dado f(n) e um tempo-limite t, qual o maior n que o algoritmo resolve nesse tempo? A receita é sempre a mesma: igualar f(n)·10⁻⁶s (tempo em microssegundos convertido pra segundos) ao tempo-limite, e isolar n.

Exemplo — f(n) = n², tempo-limite = 1 dia:

   n² · 10⁻⁶ s  =  86.400 s        (1 dia = 24·3600 s)
   n²           =  86.400 · 10⁶
   n            =  √(86.400 · 10⁶)  ≈  293.938

Exemplo — f(n) = 2ⁿ, tempo-limite = 1 século:

   2ⁿ · 10⁻⁶ s  =  100·365,25·24·3600 s  ≈ 3,156 × 10⁹ s
   2ⁿ          =  3,156 × 10¹⁵
   n            =  log₂(3,156 × 10¹⁵)  ≈  51,5   →   n = 51

Compare os dois resultados: um algoritmo quadrático resolve quase 300 mil elementos em um dia; um algoritmo exponencial mal resolve 51 elementos em um século. Essa é a distância entre "polinomial" e "exponencial" — e é o motivo pelo qual, em estrutura de dados, o objetivo quase sempre é baixar a classe de complexidade (de Θ(n²) para Θ(n log n), de Θ(n) para Θ(log n)), não só otimizar constantes.

3.6 Multiplicação de matrizes: um exemplo clássico

Somar duas matrizes n×n é Θ(n²) (dois for aninhados percorrendo cada posição uma vez). Multiplicar é mais caro: calcular um único elemento aᵢⱼ do resultado exige um produto interno de uma linha por uma coluna, Θ(n) operações — e existem n² elementos para calcular, então o total é Θ(n³) pelo algoritmo direto (o "escolar").

Curiosidade que aparece na apostila do professor

Existem algoritmos assintoticamente melhores que Θ(n³) para multiplicar matrizes (o algoritmo de Strassen chega perto de O(n^2,807)), e a pesquisa nessa área continua ativa até hoje. Não é o algoritmo que você vai implementar no curso, mas é um bom exemplo de que "óbvio" nem sempre é ótimo.

🟢 TE1. Um algoritmo tem T(n) = n³·10⁻⁶s. Se ele processa n = 10.000 em 1000 segundos, qual a constante de tempo real (ajustando a fórmula aos dados medidos)? Com essa constante, quanto tempo levaria para n = 10⁶?

tente antes de abrir
Resolução comentada
   T(n) = c·n³
   1000 = c · (10.000)³ = c · 10¹²
   c    = 1000 / 10¹²  = 10⁻⁹ s

   T(10⁶) = 10⁻⁹ · (10⁶)³ = 10⁻⁹ · 10¹⁸ = 10⁹ s ≈ 31,7 anos

Aumentar n em 100x (de 10⁴ para 10⁶) aumenta o tempo em 100³ = 1.000.000 de vezes — de 1000s para praticamente 32 anos. É o mesmo raciocínio da regra de três "certa" da seção 3.3, aplicado a um algoritmo cúbico.

🟡 TE2. Um algoritmo tem f(n) = n e um segundo tem f(n) = n log n, ambos com constante de tempo 10⁻⁶s. Para n = 10⁹, qual a razão aproximada entre os dois tempos? (use log₂(10⁹) ≈ 29,9)

tente antes de abrir
Resolução comentada
   T_linear(n)      = n · 10⁻⁶s
   T_nlogn(n)       = n log n · 10⁻⁶s

   razão = T_nlogn / T_linear = log n ≈ 29,9

O algoritmo n log n é cerca de 30 vezes mais lento que o linear nesse tamanho de entrada — bem menos dramático que a diferença entre linear e quadrático (que seria um fator de n inteiro, ou seja, um bilhão de vezes). Isso mostra por que n log n é considerado "quase tão bom quanto linear" na prática.

4. Tipo Abstrato de Dados (TAD)

4.1 A ideia central: separar uso de implementação

Um TAD é um contrato: ele diz o que uma estrutura faz (suas operações), sem amarrar quem a usa aos detalhes de como ela é implementada por dentro. Você implementa a estrutura uma vez e a reutiliza em qualquer programa futuro, sem nunca mais reescrever o código interno.

   Quem USA a estrutura                    Quem IMPLEMENTA a estrutura
   -----------------------                 ----------------------------
   newCoordenada(10, 20)                   struct Coordenada { int x, y; };
   printCoordenada(c)                      Coordenada* newCoordenada(...) {...}
   euclideanDist(c1, c2)                   void printCoordenada(...) {...}
                                            double euclideanDist(...) {...}

   Não precisa saber COMO                  Pode mudar a implementação
   funciona por dentro                     sem que o uso mude nada

Isso é o mesmo motivo pelo qual, no capítulo de pilhas, você conseguiu trocar a implementação de vetor para lista ligada sem alterar uma linha do código que usa push/pop — essa é a vantagem prática de pensar em TAD.

4.2 O padrão que se repete: struct + construtor + operações + uso

Todo TAD no curso segue as mesmas quatro etapas:

  1. Struct — define os campos que a estrutura guarda.
  2. Construtor (newAlgumaCoisa) — aloca dinamicamente e preenche os campos.
  3. Operações — funções que atuam sobre a estrutura (imprimir, calcular, comparar).
  4. Uso — o código (geralmente o main) que chama tudo isso, sem conhecer os detalhes internos.

4.3 Exemplo completo: Coordenada e Segmento

typedef struct Coordenada {
    int x, y;
} Coordenada;

Coordenada* newCoordenada(int x, int y){
    Coordenada *aux = (Coordenada*) malloc(sizeof(Coordenada));
    aux->x = x;
    aux->y = y;
    return aux;
}

void printCoordenada(Coordenada *c){
    printf("(%d,%d)", c->x, c->y);
}

double euclideanDist(Coordenada *c1, Coordenada *c2){
    double dx = (c1->x) - (c2->x);
    double dy = (c1->y) - (c2->y);
    return sqrt(dx*dx + dy*dy);
}

Repare: newCoordenada faz duas coisas e só duas — aloca com malloc e preenche os campos. Essa separação (alocar + preencher, sempre juntas numa função construtora) é a convenção que o curso todo vai seguir, e é diretamente inspirada em como construtores funcionam em linguagens orientadas a objetos, adaptada para C.

Em cima de Coordenada, o livro constrói Segmento — uma estrutura composta por duas coordenadas:

typedef struct Segmento {
    Coordenada *ini, *fim;
} Segmento;

Segmento* newSegmento(Coordenada *ini, Coordenada *fim){
    Segmento *aux = (Segmento*) malloc(sizeof(Segmento));
    aux->ini = ini;
    aux->fim = fim;
    return aux;
}

double comprimentoSegmento(Segmento *s){
    return euclideanDist(s->ini, s->fim);   /* reaproveita a operação de Coordenada */
}

Isso ilustra outro ponto importante: TADs se combinam. Segmento não reimplementa distância euclidiana — ele reusa a operação que já existe em Coordenada. Testei o exemplo completo (com main, printSegmento etc) e a saída bate exatamente com a do livro:

   (10,10)
   (20,20)
   Distancia 14.14
   [(10,10)(20,20)]
   Comprimento:14.14

4.4 Um TAD mais complexo: Polígono

O livro estende a ideia para um polígono — um vetor de coordenadas, com um contador indicando quantas estão em uso:

typedef struct Poligono {
    Coordenada *v[100];
    int top;      /* quantidade de coordenadas usadas (e a proxima posicao livre) */
} Poligono;

Repare que top tem exatamente o mesmo papel que teve na pilha com vetor: ele é ao mesmo tempo "quantos elementos existem" e "a próxima posição livre". A função que adiciona uma coordenada usa esse duplo papel de um jeito compacto:

void addCoord(Poligono *pol, Coordenada *c){
    pol->v[pol->top++] = c;   /* usa top como índice, DEPOIS incrementa */
}

E o cálculo do perímetro soma a distância entre cada coordenada e a seguinte, fechando o polígono com a distância entre a última e a primeira:

double perimetro(Poligono *pol){
    double per = 0;
    for (int i = 0; i < pol->top - 1; i++){
        per += euclideanDist(pol->v[i], pol->v[i+1]);   /* lados consecutivos */
    }
    if (pol->top > 1){
        per += euclideanDist(pol->v[0], pol->v[pol->top-1]);  /* fecha a figura */
    }
    return per;
}

Esse é exatamente o padrão de "percorrer pares consecutivos e depois fechar o ciclo" que reaparece sempre que se trabalha com figuras fechadas (polígonos, ciclos em grafos, etc).

4.5 Por que isso importa pra estrutura de dados como um todo

O motivo de o professor introduzir TAD logo na aula 3, antes de pilhas e filas, é que pilha, fila e lista ligada são TADs. "Pilha" é um contrato (empilhar, desempilhar, consultar o topo, testar se está vazia) que pode ser implementado com vetor ou lista ligada — e o código de quem usa a pilha não muda entre as duas implementações. É o mesmo princípio do Segmento reusando a distância de Coordenada: separar a interface (o que a estrutura promete fazer) da implementação (como ela faz por dentro).

🟡 TAD1. Escreva o construtor e a operação de "inverter" para uma estrutura Segmento — a operação deve trocar ini e fim de lugar, recebendo o segmento por referência (sem criar um novo).

tente antes de abrir
Resolução comentada

É a mesma técnica de "trocar duas variáveis com uma auxiliar" que você já usa em outros contextos — aqui aplicada a dois ponteiros dentro da struct, sem alocar memória nova.

🟡 TAD2. Escreva uma função de translação para Coordenada: recebe a coordenada por referência e dois deslocamentos (deltax, deltay), somando-os às posições x e y.

tente antes de abrir
Resolução comentada
void translacaoCoord(Coordenada *c, int deltax, int deltay){
    c->x += deltax;
    c->y += deltay;
}

Passar por referência (ponteiro) é essencial aqui: se a coordenada fosse recebida por valor, a função alteraria uma cópia local e o efeito desapareceria ao retornar — o mesmo problema que você já viu em pilha, quando passar a struct por valor faz push/pop não alterarem o original.

5. O que eu preciso saber para a prova

5.1 Checklist de conceitos

  • Escrever de cor as definições formais de O e Θ (as duas usam "existem constantes positivas... tal que... para todo n > n₀").
  • Provar que f(n) = O(g(n)) ou f(n) = Θ(g(n)) para um polinômio simples, assumindo n > 1 e trocando termos menores por potências do termo dominante.
  • Diferenciar O (só teto) de Θ (teto e piso) — e saber que Θ implica O, mas não o contrário.
  • Contar operações de um trecho de código (laços simples, laços aninhados) e chegar numa fórmula T(n).
  • Resolver "quanto n cabe em tempo t", isolando n numa equação com log, raiz ou potência.
  • Explicar por que regra de três direta está errada para funções não lineares.
  • Definir TAD e explicar a separação uso/implementação com um exemplo.
  • Reconhecer o padrão struct + construtor (newX) + operações + uso.

5.2 Erros e pegadinhas comuns

  1. Confundir O e Θ: dizer que algo é Θ quando só se provou o limite superior (isso é só O).
  2. Esquecer de assumir n > 1 (ou outro n₀) antes de trocar termos — sem isso, as desigualdades n ≤ n² e 1 ≤ n² não valem para todo n.
  3. Aplicar regra de três em função não linear — sempre volte para a fórmula T(n) = c·nᵏ e substitua.
  4. Esquecer de converter unidades de tempo (dia, mês, ano, século) para segundos antes de igualar à fórmula em microssegundos.
  5. Misturar log₂ com log₁₀ — para notação assintótica não importa (a diferença é uma constante), mas para os cálculos numéricos de "quanto n cabe" importa muito.
  6. Achar que TAD é sinônimo de struct — TAD é o conjunto de operações e garantias; a struct é só um detalhe de implementação.

5.3 Miniexercícios de revisão rápida

  1. Prove que 3n² + 2n = Θ(n²).
  2. Um algoritmo Θ(n) leva 2s para n=10⁶. Quanto levaria um algoritmo Θ(n²) com a mesma constante, para o mesmo n?
  3. Se dobrar o tamanho da entrada multiplica o tempo por 8, que classe de complexidade (em termos de nᵏ) esse algoritmo provavelmente tem?
  4. Explique, em uma frase, a diferença entre "usar" e "implementar" um TAD.
Respostas resumidas
  1. Assumindo n>1: 3n²+2n ≤ 3n²+2n² = 5n² (teto) e n² ≤ 3n²+2n (piso, trivial). c₁=1, c₂=5, n₀=1.
  2. 2.000.000 segundos (2s × 10⁶), já que multiplicar n por si mesmo na fórmula quadrática multiplica o tempo pelo próprio n.
  3. Cúbico — Θ(n³), porque (2n)³ = 8n³, ou seja, dobrar a entrada multiplica o tempo por 8.
  4. Usar um TAD é chamar suas operações sem saber como elas são implementadas por dentro; implementar é escrever a struct e o corpo das funções que cumprem esse contrato.
